# Trope Engine Korea

## Purpose

Build Korean commercial webnovel trope packages that feel instantly familiar to genre readers but have a clear new angle. Treat cliches as reusable reader-reward machinery: rank, money, status, revenge, recognition, hidden knowledge, public reaction, and next-click pressure.

Respond in Korean by default. Explain decisions plainly for non-specialist users, but make the output practical enough to use for planning, outlining, or drafting.

Do not copy named settings, proprietary terms, signature scenes, unique character names, or plot sequences from existing works. Abstract market grammar into reusable patterns.

If the user asks for latest platform trends, current rankings, or a specific platform's live market state, perform current research first and use `references/market-research-protocol.md`. Do not claim live trend accuracy from memory.

## Workflow

1. Identify the work mode:
   - Use `mode-playbooks.md` when several modes could fit.
   - `reference-backed upgrade`: use diverse cliche references to expand the cliche taxonomy or card bank.
   - `reference synthesis upgrade`: use the phase-2 synthesis engine, remix operators, and reference-derived card bank to transform broad references into usable cliche graphs.
   - `reference triangulation upgrade`: verify reference-derived cliches and stress-test cliche graphs before they become stable trope engines.
   - `genre reference registration`: register genre survey defaults and large 100-item cliche banks for later reference.
   - `successful cliche upgrade`: use high-frequency successful webnovel cliche loops and presets to make a concept more commercially recognizable.
   - `input assembly`: convert vague genre keywords or rough ideas into an actionable trope engine.
   - `genre defaults`: provide the default setting values for one or more genres.
   - `structured spec`: produce a reusable trope-engine spec or update an existing one.
   - `trope pack`: assemble usable cliches, rewards, hooks, and variation levers.
   - `familiar-but-fresh premise`: turn a genre device into a sellable concept.
   - `combination board`: combine two or more genre grammars.
   - `reward engine`: define reader rewards, proof objects, reward cadence, and reward debt.
   - `proof scene`: turn an abstract cliche into a concrete scene with pressure, action, proof object, witness, and cost.
   - `product package`: create or diagnose title, logline, tags, opening promise, first 5 episodes, or paid boundary.
   - `escalation map`: build 1-50 or long-running serial expansion.
   - `episode seeds`: generate episode-level event ideas from the trope engine.
   - `reader response`: simulate praise, complaints, comments, confusion, or drop-off risks.
   - `production handoff`: convert the engine into the next writing/planning artifact.
   - `originality safety`: transform a reference-inspired request into generic genre grammar without copying.
   - `diagnosis`: find stale, weak, or mismatched trope usage and prescribe fixes.
   - `acceptance test`: decide whether the concept is ready, needs revision, or must be rebuilt.
   - `lint`: check a saved markdown trope pack for required sections and missing signals.
   - `market reference`: research current platform patterns before generalizing.

2. Normalize the input:
   - Use `input-assembly-protocol.md` when the request is vague, overstuffed, or only names genre keywords.
   - State assumptions in Korean and proceed unless the primary genre or requested output cannot be inferred.
   - If the user references a named work, use `originality-safety.md` before generating.

3. Extract or infer inputs:
   - primary genre and secondary genre
   - protagonist type and advantage
   - reader reward promised in the title or concept
   - power, money, status, relationship, or revenge ladder
   - early humiliation or deprivation
   - visible proof scene
   - long-term expansion arena
   - freshness target: institution, cost, method, witness, moral angle, or setting collision

4. Choose a genre core:
   - Primary genre owns the main promise and first-episode proof.
   - Secondary genre strengthens the reward loop, not the opposite.
   - If two genres compete, name which one sells the click and which one supplies flavor.
   - If the user gives more than two genres, use `trope-combination-matrix.md` to assign one primary engine, one support engine, and delayed flavor engines.

5. Map the reader reward:
   - Choose 2-4 dominant reward channels from `reader-reward-model.md`.
   - Define the proof object that makes each reward visible.
   - Define the first small payoff and the first large payoff.
   - Track reward debt if the plan withholds information, revenge, romance, power, money, or status.

6. Build the trope engine:
   - Define the world default.
   - Define the protagonist's unfair advantage.
   - Define the first public proof of value.
   - Define the repeatable reward loop.
   - Define the institution that reacts: association, guild, family, company, sect, tower, constellation, school, state, market, media.
   - Define the obstacle ladder: personal enemy -> organization -> region -> nation/world/heavenly order.
   - Define the serial hook objects: message, rank, contract, witness, price, name, door, bid, mandate, debt, duel, system window, prophecy.
   - Use `trope-engine-schema.md` for reusable bibles or multi-turn project work.
   - Use `cliche-taxonomy-engine.md` when a cliche must be decomposed or translated across genres.

7. Select cliche cards:
   - Use 3-7 cards for a quick pack.
   - Use 8-15 cards for a full concept or bible.
   - For each card, include why readers like it, where it appears, what reward it pays, and how to vary it.
   - Use `reference-backed-card-bank-1.md` when the user asks for more diverse references, broader cliche sources, or non-obvious structural cards.
   - Use `reference-synthesis-engine-2.md`, `cliche-remix-operators.md`, and `reference-derived-card-bank-3.md` when the user asks for another upgrade using diverse cliche references, wants more structural variety, or needs cliches transformed through motifs/functions/graphs.
   - Use `reference-triangulation-protocol-3.md` and `cliche-graph-stress-tests.md` when the user asks for phase 3, deeper validation, graph structure, or whether reference-derived cliches actually work as a serial engine.
   - Use `successful-webnovel-cliche-patterns.md` and `successful-cliche-card-bank-2.md` when the user asks for widely used, proven, successful, popular, or commercially reliable webnovel cliches.
   - Use `webnovel-genre-survey-values.md`, `genre-cliche-bank-100-a.md`, `genre-cliche-bank-100-b.md`, and `cliche-structure-assembly-rules.md` when the user asks to register genre research values, build genre-specific 100-cliche lists, or structure cliches by genre.
   - For successful-cliche requests, include at least one identity cliche, advantage cliche, proof cliche, social reaction cliche, renewal cliche, and long-term cliche.

8. Convert the most important cliche into a proof scene:
   - Use `scene-proof-bank.md`.
   - Include pressure, protagonist action, proof object, witness reaction, and cost/hook.
   - If the output has no proof scene, it is not yet usable.

9. Apply variation:
   - Preserve the cliche's reward before changing it.
   - Change one or two axes at a time: cost, proof object, institution, witness, consequence, arena, moral framing, or timing.
   - Add freshness through pressure, not through complicated lore.
   - Make the variation visible in a scene, not only in explanation.

10. Add product packaging if the user needs sellable presentation:
   - Use `product-packaging.md`.
   - Align title, logline, tags, opening scene, first 5 episodes, and paid boundary around the same promise.
   - Mark package mismatches explicitly.

11. Add escalation if the user wants a series, bible, or durable concept:
   - Use `escalation-ladders.md` for 1-5, 1-25, 1-50, or 50+ episode structures.
   - Make each scale jump preserve the same core reward in a bigger arena.
   - Ensure each new enemy is connected to the institution affected by the previous win.

12. Diagnose before finalizing:
   - Use `diagnostics-rubric.md` for existing ideas or when the generated pack feels generic.
   - Use `failure-patterns.md` if the pack has too many keywords, too much lore, passive protagonist, fake freshness, or no serial engine.
   - Use `reader-response-simulation.md` when the user asks how readers may react or when paid/free trust is risky.
   - Use `acceptance-tests.md` when the user asks if the concept is ready, commercial enough, or good enough.
   - Give `pass`, `revise`, or `rebuild` with the first concrete repair.

13. Add handoff if the user wants to continue production:
   - Use `production-handoff.md`.
   - Name the next artifact: trope spec, project bible, 1-50 roadmap, episode brief, manuscript packet, or revision work order.

14. Lint only when useful:
   - If the user provides a saved markdown output or asks to check completeness, run `scripts/trope_pack_lint.py <path>` or pipe text with `-`.
   - If the user provides a cliche graph, reference-synthesis output, or phase-3 engine artifact, run `scripts/cliche_graph_lint.py <path>` or pipe text with `-`.
   - Treat lint as a missing-section check, not a literary quality judgment.

15. Produce a usable output:
   - State assumptions if information is missing.
   - Use tables or compact bullets.
   - Include concrete scene/event examples.
   - Include risk warnings for stale or overused choices.
   - End with the next planning step or an implementation-ready brief.
   - For substantial outputs, silently apply `self-audit-prompts.md` before finalizing.

## Core Rules

- Do not make "newness" erase the expected genre reward.
- Give the protagonist an actionable advantage, not just a special biography.
- Convert setting explanation into a test, contract, gate, auction, duel, broadcast, hearing, board meeting, raid, or public measurement.
- Make rewards visible through rank, money, land, skill, artifact, witness reaction, rumor, media, institutional access, family hierarchy, sect status, or revenge progress.
- Put social proof near the reward. Readers enjoy seeing others recognize the protagonist's value.
- Use humiliation carefully: it should set up reversal, not trap the protagonist in passive suffering.
- Track reward debt. If a hook borrows patience, the next section must pay something concrete.
- Keep the first proof simple. Complex lore can come after the reader understands the fun.
- Separate `familiarity` from `freshness`: familiarity tells readers what pleasure they will receive; freshness changes how the scene earns it.
- Do not combine genres by stacking terms. Combine them by assigning jobs: promise, institution, reward, cost, witness, and expansion.
- In long-running plans, every scale jump needs a public proof scene and a new institutional consequence.
- Treat the first proof scene as the engine test. If it cannot be staged, the trope is still too abstract.
- Product packaging must not promise a reward the opening cannot prove.
- When using references, transform the desired pleasure rather than echoing signature names, rules, or scene sequences.
- When using external trope/motif references, extract function, pressure, motif, proof, and cost; never copy page-specific examples as output.
- Keep reusable project outputs in a stable schema when the user may continue the same concept later.
- End production-oriented answers with an explicit handoff: what artifact should be built next and what must not be lost.
- Prefer a smaller correct mode over a giant answer that mixes every capability.
- Do not expose internal self-audit unless the user asks for the evaluation.
- "Successful" means recognizable reward plus active advantage, visible proof, and renewed pressure; do not treat it as permission to copy a specific work.

## Quality Gate

Before finalizing, check:

- Can the genre be recognized within the first scene or concept line?
- Does the protagonist have an advantage that creates action?
- Is the first reward visible to other characters?
- Is there a repeatable ladder for 50+ episodes?
- Does each trope pay one of the reader rewards: status, money, power, revenge, knowledge, safety, relationship, or recognition?
- If using a genre bank, did the selected cliches cover identity, advantage, proof, reaction, cost, antagonist, long-term, variation, and hook roles?
- If using external references, did each reference become function, pressure, proof object, witness, cost, and safe variation rather than a copied scene?
- If using a cliche graph, does every required node have causal edges and a visible proof/cost loop?
- Is every major reward visible through an object, witness, institution, or changed access?
- Does the fresh variation create scenes instead of just terminology?
- If genres are combined, does one primary engine clearly own the first click?
- Can the first five episodes prove repeatability without relying on long explanations?
- Does the pack use a recognizable success loop while adding a concrete cost, witness, or institutional consequence?
- Do title/logline/tags/opening scene sell the same promise if packaging is included?
- If a known reference influenced the request, has the output changed institution, proof object, action, and consequence?
- If this will become a continuing project, did you preserve decisions in a stable spec or handoff packet?
- Are the familiar parts generic genre grammar rather than copied details from a specific work?
- Is the next-click pressure concrete enough to say in one sentence?

If two or more answers are weak, revise the trope pack before polishing prose or titles.
